# AGENTS.md: Developer & AI Agent Context for Win Metta

Full detail and reasoning for everything below lives in [docs/prd.md](docs/prd.md) and [docs/tech-architecture.md](docs/tech-architecture.md). This file is the quick-reference summary — when it and a doc disagree, the doc is authoritative and this file is stale and should be updated.

## 1. Project Mission & Identity

Win Metta is a California 501(c)(3) nonprofit continuing an existing Burmese Theravāda Buddhist teaching community online. The platform first gives online class students and independent learners worldwide one bilingual place to find classes and Dhamma resources (Phases 0–2), then (future phases, not scheduled) digitizes the proven Let's Learn Burmese curriculum into an interactive self-paced app and grows the Dhamma Library and class archive (docs/prd.md §1–§2, §7).

- Core visual principle: high legibility, tranquil aesthetic, zero vanity metrics (no streaks/leaderboards/badges), zero algorithmic distraction.
- Core technical principle: popular, well-supported tools that volunteers can learn easily; native execution without Docker locally; strictly typed TypeScript; Unicode-only Burmese text. Offline support is a future goal, not a v1 requirement.
- Cost principle: prefer free nonprofit programs, but paid tools are fine when they save volunteer time or reduce risk.
- Phases (docs/implementation-plan.md): **0** foundation code (basic app, libraries, `en`/`my` support, lint/typecheck/test/build CI; no real pages, no deploy), **1** bilingual pages (Classes group and Dhamma Library; no hosting or deployment yet), **2** infrastructure & deployment (static hosting on S3 + CloudFront, the CI deploy workflow, Pulumi, domains, a Beta label, one production environment; the site is public), **3** Dhamma Posts (short trilingual posts as markdown files in the repo; see below and §7). **Phases 0–2 are done; Phase 3 is built on `feat/dhamma-posts` and not merged yet** (docs/implementation-plan.md §5). Later work is not numbered or scheduled; the maintainer decides it as it comes (LLB lessons, the library upload/index pipeline and class archive, accounts, native apps; see docs/implementation-plan.md §6).
- Core scope principle: Phase 1 delivers Home, About, Privacy, Classes (with Sayadaws, Dhamma Study Groups, Retreats and Zoom help) and Dhamma Library with concise curated public content and an original app design. The Dhamma Library indexes **every PDF in the S3 bucket** (folders become tags, fuzzy Burmese-aware search with MiniSearch, manifest generated by a script); curated blog-post and app links join the same index. No copied WordPress UI or bulk WordPress migration. Serve online Zoom students and anonymous independent learners worldwide. v1 is a single web app. Do not scaffold `apps/desktop` or `apps/mobile` — those are a future phase (prd.md §4.7, §7).
- **Dhamma Posts** (Phase 3): short trilingual posts (Burmese, English, Simplified Chinese) curated as markdown files in the repo, with tags and related topics, a chronological list (newest first by default), a reader-chosen post language set, share and print. No feeds, comments or WordPress import. How to add one: §7.

## 2. This Repo Is Public — Secrets & Privacy Discipline

This repo is **public** (org default per the workspace-root AGENTS.md §3, since it's product code, not an internal-ops/credentials repo). That makes the following non-optional, and it applies equally to AI agents and human contributors:

- **Never commit secrets.** Database connection strings, AWS access keys, Bunny API keys, the Better Auth secret, OAuth client secrets (Google/Facebook/Apple), SendGrid API keys — these come from environment variables or GitHub Actions/AWS secrets only, never hardcoded or checked in "temporarily to test."
- **`.gitignore` must cover env files** (`.env`, `.env.local`, etc.) *before* such a file is ever created, not added after the fact.
- **Pulumi:** commit only non-secret stack config (`Pulumi.<stack>.yaml`); secrets are set with `pulumi config set --secret` (encrypted with the AWS KMS secrets provider) or come from the environment, and anything containing connection strings or access keys never goes in git. State lives in a private S3 bucket, never in git (tech-architecture.md §8).
- **No real personal data, ever — including in fixtures or seed data.** No real student/teacher names tied to emails, phone numbers, enrollment/roster exports (e.g. from the "Let's Learn Burmese" signup form), or private Zoom credentials. Use synthetic placeholder data for anything checked into the repo. A real name or email address in public commit history is effectively permanent, even if later deleted from the working tree.
- **Public editorial content:** verified public teacher names, class descriptions, organizational facts and resource links may be used on starter pages. This does not permit private student data or real personal records in fixtures.
- **Teacher portraits and bios:** a monastic's portrait and biography that winmetta.org already publishes may be committed (`apps/web/src/assets/people/`, `src/content/teachers.json`), with the source recorded in `src/assets/SOURCES.md`; remove them on the teacher's request. Do not commit photos of lay participants (for example Zoom gallery screenshots of retreats), and never copy phone numbers, e-mail addresses, registration forms, roster spreadsheets, chat-group invites or flyers that carry contact details from retreat or class pages.
- **Exception — public class Zoom links and passcodes:** the weekly class Zoom meeting links and passcodes are already published on winmetta.org, so they may appear in class-schedule content. Anything *not* already public (private meeting IDs, host keys, retreat or one-off session credentials) stays out.
- **Check the actual diff before staging or committing anything** — don't rely on `.gitignore` alone (a file can still be force-added), and git history is very hard to truly scrub after a push. If something sensitive looks like it's about to be committed, stop and ask rather than proceeding.
- **Enable GitHub secret scanning + push protection** on this repo (free for public repos) as a backstop — not a substitute for the discipline above.

## 3. Curriculum Naming — read before touching lesson content

Don't group content by subject (e.g. a generic "Pāḷi" bucket), and always qualify a "lesson" with its curriculum code in data, URLs and UI (e.g. `llb/grade-1/…`). Organize by the **actual class name Win Metta already uses** — every curriculum gets a short `curriculum` code, and `teacher` is always a separate field (a curriculum is never modeled as belonging to its current teacher personally, since teachers can be joined or succeeded). Known curricula (tech-architecture.md §3):

| `curriculum` code | Class name (as taught today) | Current teacher |
| --- | --- | --- |
| `llb` | Let's Learn Burmese (flagship v1 curriculum) | Ven. U Garudhamma |
| `pgtp` | Pāḷi Saddā & Tipiṭaka Pāḷi (ပါဠိသဒ္ဒါ နှင့် တိပိဋကပါဠိ သင်တန်း) | Ven. U Garudhamma |
| *(unassigned)* | Sutta Piṭaka Study (မူရင်းသုတ္တန်ပိဋကတ်ပါဠိတော်ကို လေ့လာခြင်း သင်တန်း) | Ven. Kelāsa |

`llb` and `pgtp` share a teacher today but are still separate curricula. Add any new class to this table with its own code *before* digitizing its content — never reuse an existing code loosely.

## 4. Monorepo Architecture & Structure (v1)

- Package manager: npm workspaces. Orchestration: Turborepo.
- `apps/web`: Astro static web app — pages (Dhamma Library, class directory, curricula) + React islands for interactive LLB practice. Content lives in the repo as Astro content collections (Zod schemas). The only v1 app, with responsive layouts designed for both mobile and desktop. **No backend or database in v1.**
- `apps/` contains deployable applications. `infra/` contains deployment/infrastructure definitions, with the Pulumi (TypeScript) program under `infra/pulumi/`. A top-level `content/` is optional future work if curated content becomes independent; keep Astro collections in `apps/web` for now.
- `packages/*` (for example `domain`, `i18n`, `ui`) are created only when sharing becomes real — start with code inside `apps/web`. This product has no "playlists" feature, don't reintroduce that naming.
- Deferred, do not scaffold yet: `apps/api` (Fastify + PostgreSQL, likely a future phase), `apps/desktop` (Electron), `apps/mobile` (Capacitor).

## 6. Strict Coding Conventions

- **TypeScript:** strict mode, no `any` — use `unknown` with type guards.
- **Text encoding:** all Burmese text is Unicode (Myanmar block, U+1000–U+109F). No Zawgyi handling in v1 except converting legacy Zawgyi S3 filenames in the library generator, with every conversion reviewed (tech-architecture.md §5).
- **Access:** core content (LLB lessons, Dhamma Library, class directory) must work with no login, ever. Accounts are optional and only needed for cross-device progress sync (a future phase).
- **No vanity metrics:** no streaks, leaderboards, badges, or engagement-optimized UI patterns anywhere.
- **Internationalization:** build support for English (`en`) and Burmese (`my`) in Phase 0 and launch all Phase 1 pages in both, with a central extensible locale registry, keyed messages, localized content, locale-prefixed routes and a same-page language switcher. Keep interface locale, resource language and timezone separate. **Switching language changes only the locale segment of the URL** — page, search terms, filters, query parameters and fragment must stay intact, derived from the current URL when the link is activated, never cached at load. Phases 0–2 require no onboarding; optional learning-intent/density preferences come with the LLB phase (prd.md §4.1).
- **Styling:** Tailwind utility patterns + Radix/shadcn primitives (extract to `packages/ui` only once shared). Colors and component classes (`.btn`, `.card`, `.chip`, `.link`, `.nav-link`…) live in `apps/web/src/styles/global.css`; use those tokens, not new hex values. The palette is the **Win Metta Brand Kit** in Canva (#121210, #ffffff, #ede7df, #e9dfd7, #d9e8f1, #bdd2dc, #cdcecc, #959897) plus three derived tokens (`--brand`, `--text-muted`, `--border-strong`) for contrast. **Links carry no underline:** navigation and cards use pills and stretched card links, and inline links use the brand color at semibold weight (3:1 against body text), with an underline only on hover. Never use `--grey` (#959897) for text or control borders; it fails contrast. The logo files are in `apps/web/public/` (transparent PNG sizes, favicon, apple-touch icon).
- **Formatting — run Prettier only from the repo root:** use `npm run format` / `npm run lint` (or `npx prettier --write <paths>` with the shell in the repo root). Prettier reads `.prettierignore` **only from the current directory**, so running it from `apps/web` (e.g. `npx prettier --write src`) silently ignores the root ignore list and rewrites protected files: the generated `apps/web/src/library/manifest.json` and `zawgyi-review.json` (never hand-edited), `package-lock.json`, the Pulumi stack files, and `AGENTS.md`/`docs/` (planning prose, formatted by hand). `apps/web/.prettierignore` repeats the generated library files as a backstop. Before staging, check `git status` / `git diff --stat` for files you did not mean to touch, and restore any you did not edit on purpose.
- **Local dev:** `npm run dev` runs natively — no Docker, no database needed in v1. Astro allows **one dev server per project**, so a second `npm run dev` stops with "already running". **Anyone who starts a dev or preview server (agents included) must stop it before finishing:** `npm run dev:stop` for dev, `npx astro preview stop` (from `apps/web`) for preview. Don't use `pkill -f astro` — it can miss the server or hit someone else's. Start a server only when a check needs it, and say so when one is left running.
- **Analytics:** deferred beyond v1 (Phases 0–2). No analytics SDK or learner-event collection; progress remains local.
- **Devices:** design for mobile and desktop; modern-browser baseline per tech-architecture.md §2. Legacy browsers below that baseline are not required.
- **Library index:** the S3 bucket is the source of truth for files; a generator writes a committed manifest (no AWS credentials in builds or CI), and human fixes go in the overrides file. Never rename S3 objects to fix a title. Folder page URLs use the stable ids in `folders.json` (generated; if a folder is renamed in S3, edit that entry's `path` by hand to keep its id). Every folder path segment is a tag (number prefix stripped). Search and tags share one normalization: NFC, zero-width removal, ဥ/ဉ equal, Burmese and ASCII digits equal, Latin diacritics folded (never on Burmese). Burmese is tokenized with the syllable regex, not `Intl.Segmenter` (tech-architecture.md §3). **Golden search tests run against the committed manifest** (`apps/web/src/lib/library-search.test.ts`), so regenerating it after a book is renamed or removed in S3 can break a test that names that title (for example `ဓမ္မပဒ`). Fix it by pointing the test at a title that still exists; never loosen an assertion to hide a real ranking or normalization regression. Review `zawgyi-review.json` and `git diff` of the manifest on every regeneration; never hand-edit the manifest.
- **Class schedules:** show Pacific (`America/Los_Angeles`) and Myanmar (`Asia/Yangon`) by default with correct dated occurrences and daylight-saving handling. Profile timezone preferences are future work.

## 7. Dhamma Posts — adding or editing a post

Short Dhamma teachings, explanations of Pāḷi terms, sutta or Abhidhamma ideas and questions, at `/<locale>/dhamma-posts/`. Each post is **one markdown file holding every language**; the build parses it into static pages. No author field. Readers choose which post languages to read ("Read in": any of Burmese, English, Chinese, at least one), independently of the my/en interface language. The choice is remembered in localStorage and shown in the address as `?lang=my,en,zh` (codes `my`, `en`, `zh` for zh-Hans, always in that order; `lib/posts/languages.ts`). A link with `?lang=` opens in those languages and becomes the reader's remembered choice. Share (on the posts index, tag pages and post pages) copies the address with the current `?lang=`, and on the posts index also the active search (`?q=`). Listings (the index and each tag) show 50 posts per page as static pages: `…/`, `…/page/2/`, `…/oldest/`, `…/oldest/page/2/` (`POSTS_PAGE_SIZE` and `listingPages` in `lib/posts/posts.ts`). The `oldest/` pages repeat the newest-first ones in reverse, so they are `noindex` and left out of the sitemap (`astro.config.mjs`).

- **Where:** `apps/web/src/content/posts/YYYY-MM-DD-english-title-slug.md`. The file name without `.md` is the post's **permanent id and URL** (`/en/dhamma-posts/2026-10-11-meaning-of-vidhi-and-anuvada/`). The date prefix is the `created` date; the slug comes from the English title once, at creation (diacritics folded, lowercase, dashes, at most 60 characters). Editing a title later does **not** rename the file. Never rename or delete a published post's file: shared links break (the hook warns).
- **Start a post:** `npm run posts:new -- "English title"` writes the file with today's dates and the template below.
- **Format** (all three languages required, in this order; each section starts with exactly one `# Title`):

  ```markdown
  ---
  created: 2026-10-11
  updated: 2026-10-11
  tags: [Pāḷi terms, Abhidhamma]
  ---

  <!-- lang: my -->

  # Burmese title

  Burmese body (## / ### for sub-headings) …

  <!-- lang: en -->

  # English title

  English body …

  <!-- lang: zh-Hans -->

  # Simplified Chinese title

  Chinese body …
  ```

- **Rules** (`apps/web/src/lib/posts/validate.ts`): only `created`, `updated`, `tags` in frontmatter; dates are `YYYY-MM-DD`, `updated` ≥ `created`, not in the future, and the file name date equals `created`. Titles are plain text (no `*`, `_`, backticks, links). No other `#` heading inside a section, no raw HTML, and links only to http(s), mailto or relative addresses (a `javascript:` or other script link would run when clicked). Frontmatter values may be quoted, and tag lists may be `[a, b]` or `- a` lines. Burmese is Unicode (Zawgyi markers are rejected). Chinese is **Simplified**: any character OpenCC would convert from Traditional fails, with the characters listed (convert it, then have a Chinese reader check the wording). Bump `updated` whenever you change a post; the pre-commit hook fails otherwise (`lib/posts/staged.ts`, tested in `staged.test.ts`).
- **Tags:** every tag is one entry in `apps/web/src/content/post-tags.json` with a fixed slug and a name in **each** post language: `{ "slug": "pali-terms", "en": "Pāḷi terms", "my": "ပါဠိ ဝေါဟာရ", "zh-Hans": "巴利术语" }`. The slug is the tag page URL (`/<locale>/dhamma-posts/tags/pali-terms/`), so clicking the tag in Burmese, English or Chinese opens the same page. Set it once from the English name when adding a tag (lowercase, diacritics dropped, dashes) and **never change it**, so tag links keep working; names may be edited freely. The **English name is the main tag**. The Burmese and Chinese names are aliases. In a post's frontmatter, list tags by their English names (an alias or the slug also works and resolves to the same tag). Add a new tag to the registry first, with all three names. The checks reject a name that belongs to two tags (compared ignoring case, Latin diacritics and ဥ/ဉ), a tag listed twice in a post under different names, a Traditional Chinese name, a Zawgyi Burmese name and a missing, malformed or reused slug. Each language section on the page shows that language's tag names above its title.
- **Search:** the posts index has a search box over every post's titles, topic names and body text in all languages (`apps/web/src/lib/posts/search.ts`, built at build time into `post-data/*.<hash>.json`; no step to run). It shares the library's tokenizer (`apps/web/src/lib/search-text.ts`: Burmese syllable n-grams, Latin words, Chinese characters and character pairs), and converts Traditional-Chinese queries to Simplified. The query lives in `?q=` beside `?lang=`. **Golden queries** in `apps/web/src/lib/posts/search.test.ts` name real posts: if one is legitimately changed or removed, point the test at a post that still fits; never loosen an assertion to hide a ranking regression. The same file checks the index size (now about 6.6 KB gzipped per post; budget 10 KB per post, 400 KB in total, the library's budget). When it nears the budget, shrink the body index (for example fewer Burmese n-grams for body text) or split it. Changing `search-text.ts` also changes library search: its golden tests (`library-search.test.ts`) must still pass unchanged.
- **Content:** posts come from the teachers. Keep their wording; fix only formatting. Use correct Pāḷi diacritics and titles (Sayadaw, Ven., U).
- **Checks:** `npm run posts:validate` (all posts, or `-- <file>`), the `dhamma-posts` pre-commit hook (staged files), a CI step, the content loader (`apps/web/src/lib/posts/loader.ts`, so `npm run build` fails too) and the golden test in `apps/web/src/lib/posts/validate.test.ts` all apply the same rules. `npm run format` (from the repo root) fixes markdown formatting that prettier rejects.
- **Adding a language** (all of these, or links and checks silently miss it; `languages.test.ts` fails if the code lists disagree):
  1. `apps/web/src/lib/posts/languages.ts`: append the code to `postLanguages` (the display order), add its short URL code to `urlCodes`, its name message key to `postLanguageNames`, and the same code (plus any URL alias) to the `order` and `aliases` lists inside `choosePostLanguages`, which is inlined into the page head and cannot import anything.
  2. `apps/web/src/i18n/messages/en.json` and `my.json`: the language's name (the key from step 1).
  3. `apps/web/src/styles/global.css`: a `html.js:not([data-post-langs~='<code>'])` visibility rule like the existing three.
  4. `apps/web/src/content/post-tags.json`: the new name for every tag (the registry requires one per language).
  5. Every post: a `<!-- lang: <code> -->` section in the new position.

## 8. Hosting, Domains & Environments

- Environment configuration: committed `.env.example`, ignored root `.env.local` for developer machines, and GitHub `production` environment variables and secrets for CI (a `staging` environment arrives with the first API or backend). No per-deployment env files; `.env.test` only if needed later.

- `winmetta.org` (WordPress) is untouched by this repo. This platform lives at `app.winmetta.org` (Astro static site on AWS S3 + CloudFront) as a single production environment labelled Beta in the UI. There is no staging environment or PR preview host yet (they come with the first API or backend), and PR builds are workflow artifacts. The site went public on 2026-10-23 (`PUBLIC_ALLOW_INDEXING=true`); the reviews that were meant to come first are open todos in the backlog, implementation-plan.md §6.1 (tech-architecture.md §6–§7). A future `api.winmetta.org` is tentative (tech-architecture.md §10).
- Media is stored in private **AWS S3** buckets (paid; the same AWS account also hosts the site, so permanent hosting does not depend on a grant that can lapse; Azure is for occasional workloads only) and served through a **bunny.net** CDN, so most reads avoid S3 egress. In Phase 2 the existing `dhamma-library` bucket and `dhamma-library.b-cdn.net` pull zone keep serving the PDFs, outside Pulumi (`PUBLIC_LIBRARY_CDN_BASE`); new media buckets, Bunny S3 origin authentication with a read-only IAM user and a `cdn.app.winmetta.org` hostname arrive in a future phase, when something needs them. DNS for `app.winmetta.org` is a Route 53 hosted zone delegated from DreamHost (which keeps `winmetta.org` itself).
- Portability principle: avoid cloud-specific SDKs in application code; secrets from env vars. App code references only public CDN URLs; bucket access is limited to the upload script and the Bunny origin, and S3's API keeps media movable to other S3-compatible stores. The stack should be movable to another host without a rewrite if the grant situation changes.
- Infrastructure provisioning: Pulumi in TypeScript (`infra/`), not manual console clicks — same portability reasoning as above (tech-architecture.md §8).

## 10. Key CLI Commands

- `npm run dev` — starts the local dev server; if one is already running it says so and prints its URL and PID. `npm run dev -- --force` replaces it.
- `npm run dev:stop` — stops the running dev server.
- `npm run build` — builds all apps and shared packages.
- `npm run typecheck` — validates TypeScript across all projects.
- `npm run lint` — runs ESLint and checks Prettier formatting.
- `npm run format` — formats the repo with Prettier. Run it (and any `npx prettier`) from the repo root, never from `apps/web` (§6).
- `npm test` — runs unit tests (Vitest).
- `npm run test:smoke` — runs Playwright browser smoke tests; run `npm run build` first (CI does this after the build).
- `npm run posts:new -- "English title"` — starts a Dhamma post file (§7).
- `npm run posts:validate` — checks every Dhamma post and the tag registry (§7).
