# Design guide

Use the Canva **Win Metta Brand Kit** as the visual source for the main site and every mini app. The shared palette and fonts are in [AGENTS.md](../AGENTS.md) §6 and `apps/web/src/styles/global.css`. When a rule here and the code disagree, fix whichever is wrong in the same change.

Principles behind every rule: calm and legible, nothing that pulls attention for its own sake, the same thing always looks and is worded the same way, and a reader with a slow phone, a small screen or a Burmese interface is never an afterthought.

## Brand colors

Use the shared CSS tokens for the Canva kit swatches. Consult the kit before adding a new brand color and update the reference tokens when the palette changes.

| Swatches | Recommended roles |
| --- | --- |
| Ink `#121210` and paper `#ffffff` | Main text and surfaces. Use ink for text on light surfaces. |
| Sand `#ede7df` and sand-2 `#e9dfd7` | Warm backgrounds, secondary surfaces and neutral controls. |
| Sky `#d9e8f1` and mist `#bdd2dc` | Selected or highlighted controls and accents. |
| Stone `#cdcecc` and grey `#959897` | Dividers and supporting UI. Verify their contrast for each use. |

Use `--brand`, `--brand-strong`, `--text-muted` and `--border-strong` for accessible roles that need more contrast than the original swatches provide. Derive additional light surfaces from the shared swatches, and check the resulting foreground and background pairs. Aim for at least 4.5:1 for normal text and 3:1 for control boundaries where those boundaries identify the control. Use semantic colors for errors and confirmations.

The main site uses the shared site components. Mini apps use the same brand tokens and can map them onto their own mobile-first controls. Meditation Bell uses sand for neutral controls, sky for selected controls and deep blue for primary actions. The main site and mini apps use the light palette for every system appearance. Theme selection is deferred.

## 1. Clickable or not, and button or not

A reader decides what to tap by how a thing looks, so **only things that do something may look like they do something**, and **the look says what kind of thing it is.** If clicking an element does nothing, it must be a badge or plain text.

### Decide what it is

Ask in this order and stop at the first yes:

1. **Does it only show a fact** (a count, a state, a page number, a size)? A **badge**: plain muted text, with a symbol where it helps (a document before a file size, a book before a number of books). **No pill, no background, no frame**: a rounded filled shape reads as a button. Never clickable, never styled as clickable.
2. **Does it take the reader to another page** (or to a file's own page)? A **link**.
3. **Does it submit a form, or get or start something for the reader** (download or open a file, join a meeting)? A **framed button**: filled (`.btn-primary`) for the one main submit of a page or form, outline (`.btn-outline`) for the card's own action in a list (Download PDF, Open PDF at this page).
4. **Does it only act on what is already on screen** (copy, clear a search, remove a filter, reset, try again, show more, print)? A **text action**: the usual symbol, then the words, in the link color, with no frame. It is still a real `<button>` in the HTML.
5. **Is it a folder name** (a library folder, which is also a tag)? The **folder symbol before the name**, always: a clickable one is a **text action** (it filters the page in place), a folder row in the tree is a **link**, and the active filter is a plain label (`.folder-name`) with a **Remove** text action beside it. Never a filled pill.
6. **Is it a clickable topic tag** of another kind (a Dhamma post topic)? A **chip**.

If a control seems to need a frame to be noticed, the layout is the problem, not the control.

Rules that follow:

- A badge has no pointer cursor, no hover state and no `title`-only meaning: if it carries information a reader needs, the words are visible on the page (tooltips do not exist on touch screens).
- Do not turn a chip into a badge by removing its link, or a badge into a chip by adding a click. Change the class with the behaviour.
- Text actions use the symbol readers know from other sites, always with words beside it (never the icon alone) and close to it (4 px, `gap-1`; folder names 6 px), and show their result in place (the icon turns into a check, the text into "Copied"). Symbols come from `components/icons.tsx` (or the same paths inline in an Astro file); add a new one there.
- **Secondary utility links (report a problem, feedback) are asides, not content:** a quiet link at the bottom right of the card, after the content and the main action in reading and tab order, never between the title, the details and the main action. In a card with an action row, put it in the same row (`.card-actions`, with `ms-auto`, so it wraps to the right); otherwise it is the card's last element (`.card-aside`), pinned to the card's bottom right corner with little space under it (CSS makes a card that has one a column and pushes the aside to the bottom, so cards of different heights in one grid row all end on the same line), rendered only when the feature is on, so a card without it has no empty wrapper and no extra gap.
- **The same action looks the same everywhere.** Getting a library PDF is an outline button in the catalog and in a search result, in the same place in the card's action row, followed by its small extras (the size badge, the copy action). A filled `.btn-primary` is for the one main action of a page or a form, not repeated down a list. Before adding a control, find the existing one for the same action and copy it.
- At most one filled button per card or form. Order in a row: the button first, then text actions, then the quiet link at the right.
- A control that is not available is hidden, or disabled with a visible reason; it is not left clickable and silent.
- Known controls still to bring in line with this section (migrate them when a page is touched): Print and Share on posts, the feedback dialog's Cancel.

## 2. Spacing and layout

- **Vertical rhythm comes from containers, not from margins on single elements.** The page column (`.page`) spaces its children with `space-y-10` (40 px); inside a section use `space-y-4`, inside a card `space-y-3`, and for a row of items `flex flex-wrap` with `gap-2` (chips, badges) or `gap-3` (buttons).
- **An Astro island (`client:load`, `client:visible`) renders as `display: contents`**, so it is invisible to its parent's `space-y`. Wrap every island that sits directly in the page column in a plain `<div>`, or the section above and below it touch (this happened with Search inside PDFs; `book-search.spec.ts` measures the gaps).
- Use the Tailwind spacing scale; no pixel values, no spacer elements, no `<br>`.
- Content never scrolls sideways: rows `flex-wrap`, long words and URLs may wrap, and every new page or component is checked at a 375 px width (Playwright: `scrollWidth <= clientWidth`).
- Every control is at least 44 px tall and wide (`min-h-11`), with room between neighbours so a thumb hits the right one.

### Header and navigation

- **Every menu link has an icon, everywhere.** Every first-level and submenu link in the wide header bar and in the phone menu has an outline icon before its words (`NavIcon.astro`). The header order is **Dhamma Library** (with Dhamma Apps, Digital Texts and Dhamma Posts), **Mini Apps** (only with `PUBLIC_MINI_APPS`), **Classes** (with Sayadaws, Retreats and Dhamma Study Groups) and **Donate** last (only with `PUBLIC_DONATE`); Settings uses the gear, `GearIcon.astro`. A new menu or submenu link needs an icon in `NavIcon.astro`.
- **Dropdown arrow:** a drawn chevron (a rotated corner in CSS, in the muted text colour), never a ▾ text glyph, which was too small and read as a dot. It shows on the wide bar only; the phone menu lists the submenu links open.
- **Phone menu:** below 48 rem, with JavaScript, a Menu button (three lines and the word) shows and hides the navigation; without JavaScript the links stay visible. Settings moves into the menu as gear and word after the last first-level link, and the header gear is hidden then (without JavaScript the gear stays and the menu entry is hidden, so there is never a duplicate).
- **Language switch and Settings gear:** the switch is its own sand pill (`.segmented`), compact at every width (40 px buttons, small text), and the gear is a separate round icon (`.header-icon`) beside it. Both sit in one plain wrapper (`.header-tools`, no background) so they always wrap to the next line together, never apart.
- **The language switch changes only the locale segment of the address** and saves the choice (see the language rule in AGENTS.md and the Settings page); the root `/` opens the saved language.
- **Class names are shared:** the gear's class is `.header-icon`, not `.icon-link`, because `.icon-link` is the symbol-plus-text link used in cards (§8).

## 3. Headings, text and colour

- One `h1` per page. Headings go down one level at a time (`h2` for a section, `h3` inside it, `h4` for the title of a card inside an `h3` section); never pick a level for its size, style it with a class.
- Payment details a donor must notice first (the Zelle blocks on the Dāna page) use `.zelle-panel`: sky background with a brand edge, no hover, since it is information and not a control; the value to type or copy is `.zelle-address`.
- Colors come from the tokens in `global.css`; no new hex values. `--grey` (#959897) is never used for text or control borders (it fails contrast). Information is never carried by color alone.
- Set `lang` on text whose language differs from the interface (titles, snippets, tags), so screen readers and Burmese line-height rules apply.
- Numbers follow the interface language: Burmese digits in Burmese (၁၂ အုပ်, ၉.၅ MB), Latin digits in English (`formatCount`, `formatSize`; never `toString()` or a raw number in a message). A counted thing uses its counter after the number (books are `အုပ်`, not `စာအုပ်`). Dates, times and class schedules keep the Latin digits they were decided to have.

## 4. Words and translations

- Sentence case, short, plain; the same thing has the same words everywhere: **Open PDF**, **Download PDF**, **Copy citation**, **Try again**, **Show more**, **Search**. Look for an existing message key before writing a new one.
- All visible text is a message key in `en.json` and `my.json`, never a string in a component. A new Burmese text is flagged in the PR as needing a Burmese reader's review. Never copy teachings; keep titles and Pāḷi diacritics exact.
- **Secondary labels are short in both languages**, so they never take more room or attention than the content: Burmese often runs longer than English, so when the Burmese version of a secondary link or action is clearly longer, write a shorter one (the "Something wrong?" link is `အမှားပြင်ရန်`, not a full sentence). Check the Burmese page too: a secondary link should take well under a third of its row.
- Say what the reader can do next in an error ("You can still search titles and tags above"), never only what went wrong, and never show technical details or codes.

## 5. States: every control that waits has all of them

Anything that loads or can fail has four visible states, each tested:

1. **Loading**: say so in words (`aria-live="polite"`), keep the layout still.
2. **Empty**: say it plainly and suggest what to try.
3. **Error**: a short message and a **Try again** button; never wipe what is already on screen because one later request failed (a failed "Show more" keeps the pages shown).
4. **Success**: the result, with its source or limit stated where it matters (OCR text may contain mistakes; the page number is the PDF's own).

Core content works with no login and, where possible, with no JavaScript; a feature that needs JavaScript or a service says so, and the page around it keeps working when it is down.

## 6. Forms and search

- A visible label above the field; the placeholder is an example, never the label.
- Enter submits. Requests to a service are sent on submit, never on every keystroke; searches that run in the browser may update as the reader types.
- The query lives in the address (`?q=`, `?pdf=`) so a search can be shared and survives a language switch; other parameters are preserved.
- Nothing the reader types is sent to analytics or logs: events carry a count range and a script label, never the words (docs/analytics.md).

### Settings pages

Settings use the **row layout of macOS System Settings and Windows 11 Settings, not cards**: a flat list divided by hairlines (`.settings-list`), one row per setting (`.settings-row`) with its name as a bold title (`h2`, `text-xl font-bold`) and a short muted explanation on the start side (`.settings-text`) and its control on the end side: a segmented choice (`.segmented.settings-choice`, buttons with `aria-pressed`, as the post language picker) for a few options, a red `.btn-danger` (red outline and text, filled red on hover) for a destructive action such as Reset or Clear, never the blue outline of a normal action, a switch or checkbox for on/off. Rows have generous padding (`py-8`) and are separated by hairlines between rows only (none above the first or below the last), never boxed, shaded or rounded. On a narrow screen the control wraps under the text at full width. A reset needs no confirm dialog when it is cheap and reversible: it runs at once, the button is disabled (muted, `not-allowed`) whenever nothing is saved and after a reset, and a green `✓ …` line (`.settings-done`, `role="status"`) sits beside it, stacked below on a phone. A setting takes effect when changed (no Save button) and says so in a `role="status"` line; the Settings link is the header gear, which on a phone (when the Menu button shows) moves into the menu as gear and word after the last link; the page title carries the gear icon (`GearIcon`), the same one as the header link. Add a new setting as a new row, not a new card.

## 7. Calm by design

No streaks, badges for achievement, counters that invite comparison, autoplay, pop-ups or animation beyond a short transition. The `.badge` class is for facts, not for rewards.

## 8. Reuse, then verify

- **Before adding a CSS class, search for its name** (`rg "\.name\b" apps/web/src`, and in the markup): a shared name silently restyles every other use. `.icon-link` (symbol before a text link) once collided with a header gear icon and squashed every class card link; the gear is `.header-icon`.
- Use the existing classes and components first (`.btn`, `.card`, `.settings-row`, `.chip`, `.badge`, `.field`, `.link`, `Button`). Add a new class only when a second place needs it, and add it to the table in §1.
- Before opening a PR for a visual change: look at it (a screenshot at desktop and at 375 px width), in English and Burmese, and with the service stubbed as down. Add a browser test for anything that was wrong and could come back.
- If a reviewer or the maintainer finds a new kind of inconsistency, add the rule here in the same PR that fixes it.

## 9. Mini apps

Mini apps are small tools under `/<locale>/mini-apps/`. Design each as a standalone, mobile-first experience. Prefer app-specific layouts, components and interaction patterns that fit its primary task. Shared services such as localization, analytics and feedback can support each app's own interface.

- **Listing page:** a normal site page (header, footer, language switcher). Each mini app is a tile: its icon as a rounded square, 64 px, and its name below in the body font; a "Beta" or "Coming later" note as a `.badge`-style muted line, never a pill. A tile is one link (the whole tile), except a "Coming later" tile, which is not a link and does not look like one. Every tile comes from the registry (`lib/mini-apps.ts`), never hand-written markup.
- **Names:** a mini app's English name is written in Title Case everywhere it appears (listing tile, title bar, page title, messages, docs): "Meditation Bell", "Burmese Text Converter", never "Meditation bell". Decided 2026-11-26. The Burmese name has no case, so it is unchanged. New mini apps follow the same rule, and the name lives in one message key (`miniApp<Name>Name`) that the tile, title bar and page reuse. The page address (slug) stays lower-case with hyphens.
- **Analytics (decided 2026-11-26):** every mini app counts the use of each of its features with cookieless events that carry no personal information, so volunteers can see which features are popular. The rules and the checklist are in `AGENTS.md` ("New mini apps") and the events in [analytics.md](analytics.md) §3. A control without an event is a gap, so add the event when you add the control.
- **Kinds of action buttons (decided 2026-11-26):** each kind of action has its own look, so a reader can tell a harmless action from a destructive one before reading the words, and the look is the same in every mini app.
  - **Main** (Convert, Save, Submit): `.mini-button--primary`, filled with the accent colour, full size. One per panel.
  - **Standard** (Copy, Swap, Download, Share): `.mini-button`, outlined in the neutral colour, small (`.mini-button--small`) unless it must align with other components. Does not change or lose anything.
  - **Destructive** (Clear, Reset, Delete, Remove): `.mini-button--danger`, red text and red outline on white, a light red wash on hover, with an icon (the island's `CloseIcon`). Use it for anything that throws away what the reader typed or chose. Never use red for a harmless action, and never leave a destructive action in the neutral style. Keep it away from the main action; it is small and disabled when there is nothing to lose. If the loss cannot be undone and is large (more than what is on screen), ask for confirmation first.
  - Order in a row: standard actions first, destructive last. Colour is never the only signal: keep the words and the icon.
- **Compact controls (decided 2026-11-26):** a mini app uses compact controls for its secondary actions and for choices: the joined choice control (`.mini-choices`, 36 px, 0.8125 rem text, only as wide as its words) and small buttons (`.mini-button--small`, 36 px, 0.875 rem text, only as wide as their words) for Swap, Reset, Clear, Copy and the like. Reason: on a phone, full-width 44 px buttons crowd the content and make a secondary action look as important as the main one. The exception is a button that has to align or line up with other components: it keeps the full size and the width of what it lines up with, so the layout stays tidy (a main action such as Convert or Save, the button that sits in a row of fields, or one that fills the width of a form). When unsure, ask whether the button would look wrong or uneven next to its neighbours at 375 px: if not, make it compact.
- **Icons:** one set, designed in Canva from basic shapes (no stock elements): a rounded square with one flat background colour from the palette and one simple symbol, no text, gradients or shadows, legible at 32 px on the light palette. Source, export and licence rules: [meditation-bell.md](meditation-bell.md) §2.1.
- **Mini app layout:** give each app a compact title bar with a back link to the localized Mini Apps listing, its icon and name, and an accessible language picker. The title bar serves as the page heading. Keep the language picker visually distinct from the main site's switcher. Meditation Bell uses a globe menu with English and မြန်မာ.
- **Back link:** an arrow followed by the words "Mini Apps" (a cross would read as "discard", and a bare arrow as the browser's Back). Below about 360 px, and below 432 px in Burmese (its title is wider), only the arrow stays and the words remain as the accessible name. The title is centred on the page while the back link fits; when it does not, the back link wins.
- **Touch layout:** use controls with at least 44 px touch targets. Give frequent actions room and prominence. Meditation Bell uses a full-width Ring now button with a 56 px minimum height and a 24 px gap above it.
- **Feedback and navigation:** keep any Feedback control below the app content. If a timer or schedule is active, ask before the back link or a language switch leaves the page, saying what will stop (not "something is unsaved"), and save the state so the user can resume.
- **Alerts at the top:** notices and errors that concern the whole app appear in one area at the top of the app, under its main mode switch, never at the bottom. Confirmations for anything that turns something off or replaces data are not in this area: they are a centred modal `<dialog role="alertdialog">` over a dimmed page (see "Must-answer prompts"), with the safe choice (Cancel) focused; highlighted notices (`role="status"`) close after 4 seconds or with ✕. Field errors stay next to their field.
- **Pointer, keyboard and press states:** after a click or tap, buttons, links and summaries show no focus ring; any key press brings it back (`data-mini-app-input` on `<html>`, set by `MiniAppShell.astro`, rule in `global.css`). Text fields always keep their focus style. Hover colours apply only on devices that really hover (`@media (hover: hover)`), so a tap leaves no stuck hover look. A pressed button dims briefly (`:active`).
- **Errors:** a field with an error gets a red border and a light red tint, and its message sits right under it in bold red (`--danger`) with a red bar on the start side, so the cue is not colour alone. A group such as the day buttons turns its borders red. Check that no muted-text rule overrides the error colour.
- **Must-answer prompts:** something the user has to act on to continue (for example enabling sound, without which scheduled bells stay silent) is a centred modal `<dialog>` with a dimmed backdrop, one clear primary button, no Esc to dismiss, and a way out if the action fails. Prefer this to a notice that can be missed.
- **Costly settings explain first:** a setting that costs something (keeping the screen on uses battery) opens a modal when turned on that says what changes and why it is needed, with a confirm and a Cancel button. Turning it off is immediate. The explanation is translated.
- **On/Off settings:** use the app's switch (a `role="switch"` button with the track and the words On or Off, as for Weekly schedule), with the switch before its label, not a checkbox. When the setting has no effect (the schedule is off), disable it and say why in a muted line under it; keep the choice, and save it, so it is still there when the setting matters again.
- **Status and next step:** an app that runs by itself shows that it is running and what happens next, at the top of its view: a dot and "Running", then the next event ("Next bell: Today 2:22 PM · label", "in 2 h 22 min"); when off, one plain line saying nothing will happen. The same dot sits on the mode tab so it shows from the other view, and the next item is tagged "Next" in its list. Time words are short and English ("in 5 min", "1 d 3 h").
- **Lists:** a row of repeated items uses fixed columns, with what it applies to first (days), then the time, then the label. The first two columns have equal, fixed widths; the label takes the rest and wraps so every character shows (never an ellipsis for something the user typed). Several days summarize as "Every day", "Weekdays" or "Mon–Wed, Sat".
- **Display ring:** the countdown ring is about 14.5 rem with a 6 unit stroke so it does not crowd the controls; the digits are centred on the glyphs, not the line box (`text-box: trim-both cap alphabetic`), and the status word ("Ready", "Paused") sits at the bottom inside the ring and is empty while running. Three-digit minutes use a smaller size so they stay inside.
- **Language exception:** a mini app may keep its buttons and labels in English in both locales and translate only alerts, notices and errors, as the meditation bell does ([meditation-bell.md](meditation-bell.md) §7.1). It is still all message keys (the `my` value is the English text), action buttons pair words with icons, and it is a decision written in the mini app's own doc, not a default. The listing page is always fully translated.
- **Digits and day names:** Western digits for times, dates and numbers in both locales. Meditation Bell uses three-letter day labels such as "Mon", with the full name in the accessible label, messages and alerts. Its timer uses larger tabular digits, with milliseconds set smaller than the minutes and seconds.
- **Narrow screens:** rows of equal buttons (days, presets) use `minmax(0, 1fr)` grid columns so nothing is pushed off screen; fixed labels end with an ellipsis, but text the user typed wraps. Check every mini app at 320 px as well as 375 px and desktop, in both locales.
- **Calm (§7) applies in full:** no streaks, totals of time spent, badges or celebration animations. A bell may move a little when it rings; nothing else animates.

### Building a mini app: the shared look

A new mini app uses the shared `mini-*` classes in `apps/web/src/styles/mini-app.css`, which carry the Meditation Bell's look (its own surface and ink colours, 44 px controls, a title bar with back link and globe menu). Do not write a new look, and do not use the site's `.btn`, `.field`, `.card`, `.badge` or `<select class="field">` inside a mini app. The bell's own `bell-*` classes (`meditation-bell.css`) are left as they are for now; they should move onto the `mini-*` classes in a later change, and until then a change to one look is made in both files.

- **Page:** `MiniAppShell` with `<MiniAppHeader slot="app-header" …>` (title bar: back link, icon, name, language menu) and `import '../styles/mini-app.css'`. A tool with two side-by-side panes passes `wide` (content up to 60 rem from 900 px; the default stays the narrow phone column).
- **Classes:** `.mini-panel` (a framed group of controls), `.mini-label` (visible label above a field), `.mini-field` (text input, `<textarea>`, `<select>`), `.mini-button` (outlined 44 px button; an icon before its words, as in the island's `MiniButton`), `.mini-button--primary` (the one main action, filled), `.mini-button--danger` (destructive action: red, see "Kinds of action buttons"), `.mini-button--small` (a compact secondary action such as Swap, Reset, Clear or Copy: see "Compact controls"), `.mini-choices` with `.mini-choice` buttons (a joined choice control, see Choices), `.mini-help` (muted help text), `.mini-notice` (neutral notice), `.mini-error` (red bar and bold red text, with `aria-invalid="true"` on the field it describes).
- **Dropdowns:** `<select class="mini-field">` only. The rule draws the arrow itself as a 1.25 rem chevron set in from the right border and removes the browser arrow (`appearance: none`); never ship a bare `<select>` whose small native arrow touches the border.
- **Choices:** the default control for picking one option is the native `<select class="mini-field">`: the phone opens its own picker, it takes one line however long the names are, and it works in every language. Use a checkbox for on or off. Buttons are allowed (as `.mini-choices`, below) only for a choice that is the main control of its panel, has two or three short options, and still fits one line at 375 px in English and Burmese; never for a secondary setting, a longer list or something that would wrap. Whichever you use, give it a visible label (the word "Font" before the dropdown, not only an `aria-label`). If the choice changes how something looks, say so where it shows: a short caption under that box ("Shown in Zawgyi-One"), updated as the choice changes, so the reader sees what the setting did.
- **Choice buttons look like one control:** wrap two or three `.mini-choice` buttons (`aria-pressed`) in `<div class="mini-choices" role="group" aria-label="…">`. They share one frame and are divided by thin lines, only as wide as their words need (never full width), 36 px high with 0.8125 rem text (a secondary control, so smaller than the 44 px buttons). An unselected one looks raised (light top edge, darker bottom edge); the selected one looks pressed in (sunk, darker, accent text), so it reads as "on" without relying on colour alone. No gaps, no separate rounded corners per button.
- **Mobile first:** design at 375 px and let wide screens add columns, not the reverse. A primary control is at least 44 px high (the `.mini-*` classes do this); a small secondary control may be smaller, but never below 36 px. Keep every control to one line of text and let groups stack in one column on a phone. Do not rely on hover, drag or small icons alone. Never add a component library: use the native controls and `mini-*` classes, which keep every mini app looking the same and cost no dependencies. Where two boxes sit side by side, share grid rows (`md:grid-rows-subgrid`) so their labels, boxes and buttons line up.
- **Long text:** a textarea that can hold text without spaces (Burmese, pasted data) gets `break-all`, so one huge word cannot freeze the page.
- **Spacing:** components never touch: text, panels, fields and buttons are always separated by space. Put them in a `.mini-stack` (a grid with a 1.25 rem gap) or another `gap` container and let the gap do the work. Do not add `mt-*`, `mb-*` or `pb-*` utilities to `mini-*` classes: those classes set `margin: 0` and their unlayered rule beats Tailwind's layered utilities, so the margin silently does nothing (the converter's intro line once sat flush against its panel). Check every new component for a gap above and below it, at desktop and at 375 px.
- **Burmese fonts:** text in a legacy encoding is shown in its own font so it reads correctly: `font-zawgyi` and `font-win-innwa` (`styles/burmese-fonts.css`; the files are in `public/fonts/`, downloaded only when used). Put the class on the field that holds that encoding and `translate="no"`. Never convert text just because the font changed.
- **Messages:** put notices and errors in one `role="status"` `aria-live="polite"` area below the controls they concern, using `.mini-error`, `.mini-notice` and `.mini-help`; do not invent colours.
- **Colours:** use the `--mini-*` variables (`--mini-surface`, `--mini-ink`, `--mini-quiet`, `--mini-line`, `--mini-accent`, …), never hard-coded hex values, so light and dark stay consistent.
- **Check before a PR:** screenshots at desktop and 375 px in English and Burmese; compare the header, a dropdown and a button with the Meditation Bell side by side, and check that every control can be tapped with a thumb.
